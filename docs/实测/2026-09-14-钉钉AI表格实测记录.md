## 四、踩到的坑与确认的行为

### 4.1 组织级拦阻（阻断多账号）

新登录走到 Step 4 被拦：

```
CLI data access is not enabled for this organization
```

**处理**：需组织主管理员在钉钉开放平台开启「允许成员通过 CLI 访问个人数据」。
**这是组织管理动作，不是技术配置。**

**异常观察**：现有登录在该开关未开的情况下**仍可用**（`auth status` 有效、数据可读）。
新登录被拦而旧会话可用——根因未查明，**推测**与旧会话持开关开启前签发的凭证有关。
**未解，留待管理员核对开关真实状态。**

### 4.2 设备流不输出二维码

`dws auth login --device` **不产生二维码**，只输出带 `user_code` 的深链。

**应对**：插件宿主侧用本地 `qrcode` 包把深链画成 SVG data URL，前端渲染 `<img>`。
**绝不调用第三方二维码服务**——认证链接不外发。解析失败时降级为「只显示深链 + 授权码」。

### 4.3 本机已登录时设备流可能免扫码

本机处于钉钉登录态时，设备流可直接选定对应账号与企业组织、无需扫码即完成授权。

**易误读为"系统自动批准"** —— 不是。是本机登录态导致。
**推论**：在已登录机器上点「扫码绑定」可能不弹码直接完成，用的是**本机当前选定**的账号/组织。

### 4.4 探针模式不是零副作用

`probeMs > 0` 的「探测输出」动作会在若干毫秒后杀掉会话。
若组织已开启 CLI 访问，**探测即可能真的新增账号**——它不是一个纯观察动作。

### 4.5 钉钉侧没有"列出全部 Base"的接口

- `base list` 只返回**最近访问**过的 Base
- `base search` 每次约 **4 条**，且返回的 `hasMore: true` 是**误报**（游标翻页无效）

**结论**：扫描产出是「多渠道候选 ∪ 人工补录」，**不保证穷尽**。多给关键词，或直接给 `baseId` 补录。

### 4.6 权限判定用实测而非模型解析

不解析角色权限模型，而是**跑一次 `base get`**：成功即可读，失败则记录真实原因。

### 4.7 CSV 必须带 BOM，且要回读自证

导出的 CSV 以 `\uFEFF`（`EF BB BF`）开头——这是 Excel 正确识别 UTF-8 中文的**唯一**条件。

**陷阱**：编辑器看不见 BOM，`ripgrep` 还会主动剥掉它。
**应对**：插件落盘后**回读首 3 字节**自证。筛选写入的 CSV 列以**字段目录**为准（全量字段、固定顺序），
否则空列被省略、列集会随数据漂移，下游按列位解析会错位。

## 五、本次实测确认的架构约束

### 5.1 `connection` 必须走 scoped 注入

`connection` 服务**只存在于 web 平面**。若写进插件顶层 `inject = ['tools', 'connection']`，
则在 headless / tui 等无 web 连接的 profile 里，**整个插件会永远停在 `inactive`，10 个工具一起消失**。

**正确写法**：顶层 `inject = ['tools']`，用 `ctx.inject(['connection'], cb)` 开子 fiber。

**自证方式**：`dingtalk_aitable_diagnose` 返回的 `rpcEndpoint.registered` 为 `true` 才算挂上。

### 5.2 写门禁双锁

`allowWrite`（create/update）与 `allowDelete`（delete）**默认全关**；
删除另需**逐次** `confirm: true`。

### 5.3 定时器跑在 Host 进程内

`dws`/DSH 关着时定时任务**不执行**，重启后自动重算下次触发点。
**这是登记在案的接受语义，不是缺陷。**
